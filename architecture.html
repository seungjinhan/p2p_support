서버 경유 0% 무제한 P2P 고속 전송의 원리

WebRTC DataChannel, MQTT WebSocket 시그널링, 9-Byte 커스텀 바이너리 프로토콜, 그리고 SHA-256 채널 격리 기술이 결합된 브라우저 P2P 네트워크의 동작 구조를 상세히 해설합니다.

1

클라이언트-서버 모델 vs P2P(WebRTC) 모델

우리가 일상에서 쓰는 클라우드(구글 드라이브, 카카오톡 등)는 중앙 서버에 파일을 업로드한 뒤 상대방이 내려받는 구조입니다. 반면 P2P Direct Share는 파일이 서버에 전혀 올라가지 않고 기기간 1:1 직통 통신로를 통해 즉시 스트리밍됩니다.

❌ 전통적인 클라이언트-서버 전송
  • ⚠️ 2배의 시간 소요: 업로드(A➔서버) 완료 후 다운로드(서버➔B) 시작
  • ⚠️ 비싼 서버 인프라 비용: 트래픽당 AWS/GCP 전송료 발생
  • ⚠️ 용량 제한: 서버 스토리지 및 메모리 한계로 파일 크기 제한
  • ⚠️ 보안 및 사생활 유출 위험: 중앙 서버에 내 파일이 저장됨
✅ P2P Direct Share (WebRTC 직통)
  • ⚡ 초고속 1:1 전송: 실시간 스트리밍으로 딜레이 최소화
  • 💰 서버 유지비 0원: 데이터가 서버를 거치지 않아 비용 무료
  • 🚀 무제한 용량 전송: 10GB, 50GB 대용량도 브라우저 메모리 고갈 없이 전송
  • 🔒 E2EE(종단간 암호화) 보안: 오직 수신자 기기에서만 복호화

통신 연결 전체 라이프사이클 (4-Step Lifecycle)

공유기(NAT)나 사설망 뒤에 숨어있는 두 기기가 서로의 위치를 찾고 안전하게 1:1 연결을 맺는 전체 과정입니다.

sequenceDiagram autonumber actor A as 💻 Host (방 생성자) participant Broker as 📡 Signaling Broker (MQTT) participant STUN as 🌐 STUN/TURN 서버 actor B as 📱 Guest (참여자) Note over A,B: [1단계] SHA-256 채널 격리 및 방 개설 A->>A: SHA256(방키 + 비밀번호)로 채널 토픽 유도 A->>Broker: "p2pshare/v8/ABC123_hash/#" 토픽 구독 및 대기 Note over A,B: [2단계] QR 스캔 및 상호 존재 감지 (Signaling) B->>B: QR 스캔 후 동일한 비밀번호 입력 B->>Broker: "p2pshare/v8/ABC123_hash/presence" 브로드캐스트 Broker-->>A: B 기기 접속 알림 전달 (💻 1:1 연결 감지) Note over A,B: [3단계] NAT 관통 및 WebRTC 악수 (Handshake) A->>STUN: "내 공인 IP와 포트가 뭐야?" (ICE Candidate 수집) B->>STUN: "내 공인 IP와 포트가 뭐야?" A->>Broker: 통신 제안서(SDP Offer) 전송 Broker->>B: SDP Offer 전달 B->>Broker: 통신 수락서(SDP Answer) 전송 Broker->>A: SDP Answer 전달 Note over A,B: [4단계] 1:1 직통 P2P DataChannel 개통 (중매쟁이 이탈) A->>B: ⚡ WebRTC SCTP 1:1 직통 통신로 연결 완료! (서버 완전 배제)
💡 Signaling(시그널링)이란?
두 기기가 직접 연결되기 전까지는 서로의 공인 IP나 포트를 알 수 없습니다. 따라서 처음에만 가벼운 중매쟁이(MQTT Signaling Broker)를 통해 "내 통신 정보(SDP/ICE)는 이거야"라는 명함만 딱 1번 주고받고, 연결이 체결된 즉시 중매쟁이를 떠나 둘이서만 1:1로 직접 통신합니다.
3

9-Byte 커스텀 바이너리 프로토콜 (초고속 전송 규격)

웹 개발에서 널리 쓰이는 JSON.stringify()나 Base64는 33% 이상의 메모리 낭비와 극심한 CPU 직렬화 지연을 발생시킵니다. 본 시스템은 C/Go 언어 수준의 초경량 9바이트 Big-Endian 바이너리 헤더를 자체 설계하여 메모리 복사 없이 초고속으로 스트리밍합니다.

[Byte 0]
Type (패킷 종류)
Uint8 (1 Byte)
[Byte 1 ~ 4]
File ID (파일 번호)
Uint32 Big-Endian (4 Byte)
[Byte 5 ~ 8]
Seq / Length (순번)
Uint32 Big-Endian (4 Byte)
[Byte 9 ~ N]
Payload (실제 데이터)
Raw ArrayBuffer (최대 16 KB)
타입 코드 명칭 역할 및 동작 설명
0x01 CHAT 실시간 텍스트 메시지 및 클립보드 공유 전송
0x02 FILE_META 파일 이름, 전체 크기, 총 청크(조각) 수 메타데이터 전송
0x03 FILE_CHUNK 16KB 단위의 바이너리 파일 조각 실시간 스트리밍
0x05 FILE_CANCEL 전송 중단 즉시 수신측 버퍼 및 메모리를 해제하는 9바이트 취소 신호
0x06 / 0x07 PING / PONG 네트워크 레이턴시(RTT ms) 측정 및 실시간 연결 상태 감시
🔧 JavaScript 구현 핵심 (protocol.js): 
// 9-Byte Binary Header 인코딩 예시
const buffer = new ArrayBuffer(9 + chunkData.byteLength);
const view = new DataView(buffer);

view.setUint8(0, 0x03);                 // [Type: FILE_CHUNK]
view.setUint32(1, fileId, false);       // [FileID: 4-Byte Big-Endian]
view.setUint32(5, chunkIndex, false);   // [ChunkIndex: 4-Byte Big-Endian]

new Uint8Array(buffer, 9).set(new Uint8Array(chunkData));
dataChannel.send(buffer); // Zero-Copy Direct Transmission!
4

전이중(Full-Duplex) 동시 전송 & 브라우저 버퍼 제어

양쪽 기기에서 대용량 파일을 동시에 서로에게 보낼 때 연결이 끊기거나 멈추지 않는 핵심 비결입니다.

flowchart TD Start([파일 전송 시작]) --> Slice[16KB 조각 슬라이싱] Slice --> CheckBuf{WebRTC 버퍼 > 256KB?} CheckBuf -- Yes --> Drain[onbufferedamountlow 대기 (이벤트 루프 해제)] Drain --> CheckBuf CheckBuf -- No --> Send[dataChannel.send 패킷 송출] Send --> Yield{2개 청크 전송 완료?} Yield -- Yes --> Sleep[4ms Event Loop Yielding
상대방 수신 패킷 & 하트비트 처리] Yield -- No --> NextChunk Sleep --> NextChunk{모든 조각 전송 완료?} NextChunk -- No --> Slice NextChunk -- Yes --> Complete([전송 완료 및 로그 기록]) style Sleep fill:#0369a1,stroke:#38bdf8,color:#fff style Drain fill:#92400e,stroke:#f59e0b,color:#fff
⚡ 16KB 표준 청킹 & 4ms Yielding

브라우저의 자바스크립트는 싱글 스레드입니다. 송신 루프 사이에 await new Promise(r => setTimeout(r, 4))를 적응형으로 배치하여, 내가 보내는 중에도 상대방이 보내오는 데이터를 실시간으로 수신합니다.

💓 모든 패킷의 능동 하트비트화

파일 데이터 청크가 들어오는 것 자체가 상대방이 살아있다는 증거이므로, 모든 수신 패킷마다 `lastSeen` 타임스탬프를 갱신하여 대용량 전송 중 타이머 오판으로 인한 연결 끊김을 완벽히 방지합니다.

🔒 원천 침입 차단 원리:
비밀번호가 1글자라도 틀리면 SHA-256 해시 결과가 완전히 달라져 전혀 다른 채널 토픽에 접속하게 됩니다. 따라서 제3자가 임의로 6자리 방 키를 무작위 대입하더라도 패스워드를 모르면 통신 신호 자체를 도청하거나 방에 들어올 수 없습니다.
